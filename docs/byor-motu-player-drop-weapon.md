# Source player weapon-loss selection

The generic no-attached-item dropweapon(1) helper now supports a player target in an isolated private code path. It reads the typed player index, chooses the stored weapon number when nonzero and otherwise uses the level weapon, then calls the existing actual native weapon resolver and same-model transition. A positive second weapon-loss override is evaluated after a completed same-model first call. Bookkeeping preserves the source rule: WEAPLOSS_TYPE_CHANGE stores the requested number, while other policies store the level setting.

The unchanged pinned C dropweapon/set_weapon bodies pass 16,800 selection and player-bookkeeping cases. Model transition is instrumented in this authority; a second call using changed modeldata is explicitly unproven. The native helper passes 874 cases across physical slots 0/63/127, player indices 0/3, full-width signed weapon requests, level fallback, list identities, first loss policy and second override. Actor, view, model-cache, player/stat rows and CPU context are compared. The inherited nonplayer tests also pass through this helper, retaining explicit attached-item and different-model requirements.

Player branch entry guards reject invalid player tags, reserved/high words, out-of-range indices, invalid player capacity and stale lifecycle/transition state before player writes. The new helper is emitted outside bank 0 from the existing native body, with checked source shape. The production helper and original static presentation path are unchanged. No PCM copies or color reduction were applied.

This closes player selection/bookkeeping only. A different selected model still returns a required service before the model body; attached items remain required. Full model transition, palette reset, damage callback acceptance and production-world integration remain unbound. MOTU gameplay and Demo completion are not certified.
